## ③ 신뢰성 정의: 정해야 할 질문

1. **판별:** EXPECTED_EVENT로 판정했는데 실제로는 장애였던 경우(놓친 장애)와 그 반대(오경보) 중 무엇이 더 치명적인가? → 지표의 가중치
2. **RCA:** MATCH만 정답으로 볼 것인가, PARTIAL도 인정할 것인가?
3. **라우팅:** 허용할 수 있는 오라우팅률은? 오라우팅됐을 때 되돌리는 경로는?
4. **근거 패키지:** 라우팅할 때 반드시 첨부할 항목. 예: 증거 메트릭과 로그, 배제한 가설, Topology 경로, 변경 이력
5. **자동화 단계:** 사람 검증을 언제부터 줄일 것인가? 예: "판별 정확도 95% 이상, 오라우팅 5% 이하로 4주 유지"
6. **정답셋:** 몇 건으로, 누가 라벨링하고, 얼마나 자주 다시 평가하는가?

## ④ 예상 PoC 형태 (예시)

> 기존 비즈니스 메트릭 알림 →(webhook) DevOps Agent 판별+RCA (+이벤트 컨텍스트 MCP) → Slack 리포트 → 근거 패키지와 함께 도메인 owner에게 라우팅.
> 서비스 1개로 범위를 좁히고, 과거 인시던트 N건을 재현해 [확장 C](../part2/ext-eval.md)로 정확도를 측정합니다.
